# JSON Configuration Addendum

This addendum extends `tools/code_metrics_plan.md` and
`tools/code_metrics_report_plan.md`. The three documents form the implementation
plan for the generalized tool.

## Decision

Add a `code_metrics.json` sidecar next to `code_metrics.py`:

```text
repo/
  tools/
    code_metrics.py
    code_metrics.json
```

The sidecar contains the repository's normal scanning, threshold, terminal, and
Markdown-report settings. Explicit command-line values override the sidecar.
This keeps everyday use short while allowing one-off runs without editing
project configuration.

The script remains usable if the adjacent sidecar is absent by falling back to
the same built-in defaults. This is a portability fallback, not a second source
of repository policy. The checked-in sidecar is the visible, editable policy
for repositories that use it.

```json
  },

```

JSON is intentionally used without comments so the file is accepted by the
standard library's `json` module. The field names and a generated
`--show-config` view provide the discoverability that comments otherwise would.

## What belongs in configuration

The sidecar owns values that a repository could reasonably choose differently:

- default scan target;
- whether the standard exclusion set is active;
- exact default excluded directory names;
- wildcard directory exclusions;
- repository-specific excluded paths;
- total-line threshold;
- code-line threshold;
- classes-per-file threshold;
- function/method span threshold;
- default terminal sort;
- color policy;
- whether terminal output normally shows only problems;
- whether findings normally produce a failing status;
- whether a Markdown report is generated by default;
- default Markdown report destination; and
- whether accepted findings are included in that report.

Separating `lines` and `code_lines` preserves the current default behavior while
allowing a repository to distinguish physical file size from executable-source
size.

Thresholds are inclusive limits: a finding occurs only when the measured value
is greater than the configured value, matching current behavior. `classes` may
be zero. The other thresholds must be positive integers. A threshold may be
`null` to disable that category entirely; disabled findings must disappear from
the table styling, summaries, `--problems-only`, exit status, and Markdown
report.

## What remains invariant

Do not make every implementation detail configurable. These rules define the
meaning and safety of the tool:

- Python remains the analyzed language and `.py` remains the source suffix.
- Repository-root discovery remains anchored to the script's `tools/` location.
- Relative config, target, exclusion, and report paths are repository-root
  relative.
- Directory symlinks are not followed, preventing cycles and scans outside the
  requested tree.
- Code/comment/docstring classification semantics remain fixed.
- Function-versus-method classification remains fixed.
- Acceptance marker syntax and names remain stable.
- Table columns and the report's evidence-versus-suggestion distinction remain
  stable.
- Report priority ordering remains documented and deterministic.
- File writes remain atomic.

These are contracts, not project preferences. Making them arbitrary JSON knobs
would complicate testing and allow two reports labeled with the same metrics to
mean different things.

## Configuration discovery

Resolution order:

1. `--no-config` disables sidecar loading and uses built-in defaults.
2. `--config PATH` loads the explicitly selected file. A relative `PATH` is
   resolved from the repository root.
3. Otherwise, load `code_metrics.json` beside the script when it exists.
4. If no adjacent sidecar exists, use built-in defaults without failing.

Supplying both `--config` and `--no-config` is a usage error. A missing file
selected explicitly with `--config`, unlike an absent automatic sidecar, is an
error.

Configuration is read once before target resolution. The resolved configuration
path and whether fallback defaults were used become part of the effective
configuration and Markdown scope section.

## Precedence and merge rules

Precedence from lowest to highest:

1. built-in defaults;
2. values present in the selected JSON sidecar; and
3. values explicitly supplied on the command line.

Object sections are merged by named field, so a sidecar may specify only the
values it wants to change. Scalar CLI options replace the corresponding merged
value.

Exclusions use deliberate additive behavior:

- `scan.excluded_directory_names` and
  `scan.excluded_directory_patterns` replace the corresponding built-in arrays
  when present, making the sidecar authoritative for the default pruning set.
- `scan.exclude_paths` contains repository-specific paths or glob patterns.
- Each CLI `--exclude PATTERN` adds another repository-specific exclusion.
- `--clear-excludes` clears `scan.exclude_paths` before applying CLI
  `--exclude` values; it does not clear the standard directory arrays.
- `--no-default-excludes` overrides `scan.use_default_exclusions` for one run.
- `--default-excludes` explicitly re-enables them when the sidecar disables
  them.

This provides both easy additive use and a precise escape hatch without hidden
list replacement.

## CLI overrides

Extend the planned interface with:

```text
--config PATH
--no-config
--show-config
--clear-excludes
--default-excludes | --no-default-excludes
--line-limit N | --no-line-limit
--code-line-limit N | --no-code-line-limit
--class-limit N | --no-class-limit
--function-line-limit N | --no-function-line-limit
--sort COLUMN
--color | --no-color
--problems-only | --all-files
--fail-on-problems | --no-fail-on-problems
--report [PATH] | --no-report
--include-accepted-findings | --exclude-accepted-findings
```

The positive and negative forms are necessary because "CLI overrides config"
must work in both directions. For example, a repository may enable reports and
failing status by default while a developer temporarily runs:

```text
python tools/code_metrics.py --no-report --no-fail-on-problems
```

The positional target and compatibility `--path` option override `scan.target`.
`--report PATH` overrides both `report.enabled` and `report.path`; bare
`--report` enables the configured report path.

Parser defaults for configurable arguments must be `None` or another explicit
"not supplied" sentinel. Otherwise `argparse` defaults could accidentally
overwrite sidecar values even when the user did not type the option.

`--show-config` prints the fully merged effective configuration as formatted
JSON and exits without scanning. It should include resolved repository-relative
values where useful, but should avoid machine-specific absolute paths unless an
absolute path was explicitly configured. This provides a direct way to verify
which defaults, sidecar values, and CLI overrides won.

## Validation and errors

Configuration errors must fail before scanning with the config path and a
concise field-specific diagnostic. Validate:

- top-level JSON is an object;
- `schema_version` is exactly `1`;
- section and field names are known;
- value types are exact enough to reject booleans where integers are expected;
- thresholds satisfy their range rules or are `null`;
- `terminal.sort` is a supported sort column;
- `terminal.color` is `"auto"`, `"always"`, or `"never"`;
- array members are nonempty strings;
- relative paths do not escape the repository root through `..`; and
- an output path is not an existing directory.

Unknown keys should be errors rather than silently ignored typos. Error
messages should use dotted field names such as
`thresholds.definition_lines must be a positive integer or null`.

Do not silently repair malformed configuration. No scan or report write should
begin until the entire effective configuration is valid.

## Internal design

Add immutable dataclasses representing validated configuration:

- `ScanConfig`;
- `Thresholds`;
- `TerminalConfig`;
- `MarkdownReportConfig`; and
- `EffectiveConfig`, which composes the four sections and records config-source
  metadata.

Use a single pipeline:

```text
built-in defaults
  -> load and validate JSON overrides
  -> apply explicit CLI overrides
  -> validate cross-field rules
  -> EffectiveConfig
  -> discover, analyze, evaluate, render, and choose exit status
```

Downstream functions receive the relevant immutable configuration object. They
must not inspect raw dictionaries, re-read JSON, or consult `argparse.Namespace`
directly. This keeps configuration handling separate from analysis and avoids
policy drift between terminal and Markdown output.

## Tests to add

- Adjacent `code_metrics.json` is discovered beside the script.
- An absent automatic sidecar falls back cleanly.
- `--config` resolves relative to the repository root.
- An explicitly selected missing config fails.
- `--no-config` bypasses an adjacent config.
- `--config` and `--no-config` together are rejected.
- Partial section objects merge with built-in defaults.
- Unknown sections and fields are rejected with dotted diagnostics.
- Invalid JSON, schema version, types, threshold ranges, sort values, and color
  values are rejected before scanning.
- Booleans are rejected as threshold integers.
- Each scalar CLI option overrides its JSON value.
- Each negative CLI option can disable a true/enabled JSON value.
- Positional target and `--path` override `scan.target`.
- Configured standard exclusion arrays replace the built-in arrays.
- Config `exclude_paths` and CLI `--exclude` values combine additively.
- `--clear-excludes` clears only repository-specific config exclusions.
- CLI can enable or disable the standard exclusion set.
- Relative paths cannot escape the repository root.
- Each `null` threshold disables its finding everywhere.
- Separate total-line and code-line thresholds are evaluated correctly.
- Bare `--report` uses the configured report path.
- `--report PATH` overrides the configured enabled state and destination.
- `--no-report` suppresses a report enabled by configuration.
- `--show-config` is deterministic and performs no scan or write.
- The Markdown scope section records effective settings and config provenance.

## Validation additions

During implementation, manually exercise:

```text
python tools/code_metrics.py --show-config
python tools/code_metrics.py color_tools --line-limit 600
python tools/code_metrics.py --exclude "tooling/**" --show-config
python tools/code_metrics.py --no-config --show-config
python tools/code_metrics.py --config tools/code_metrics.json --report
```

Copy both `code_metrics.py` and `code_metrics.json` back to the other repository
for compatibility testing. Confirm that its policy can be changed through JSON
without modifying the script and that its existing `--path` invocation still
works.
